## 1. Authority and Scope

This document translates the supplied V1 policy into the authoritative operation-level contract for future Flutter UI capability checks, Firestore Security Rules, trusted execution, and authorization tests.

It implements the boundaries of [ARCHITECTURE.md](ARCHITECTURE.md), [PERMISSIONS.md](PERMISSIONS.md), [DATA_MODEL.md](DATA_MODEL.md), and [AUTH_AND_SECURITY.md](AUTH_AND_SECURITY.md). It incorporates the approved v1.2.1 schema/policy decisions and does not implement any feature. Specific V1 decisions here resolve the earlier conditional grants: committee donor creation/donation recording are allowed; committee/member donation-history reads and leader audit-log reads are denied.

Only these application access roles exist:

- developer_admin
- leader
- executive
- committee
- member

users.access_role is the ONLY current application authorization authority. Committee position, historical assignment, term, translated label, client assertion, audit history, and user_directory are never authorization inputs. No role inherits an unlisted capability implicitly.

ALLOW in a row means eligible only when every scope, field, prerequisite, transition, and enforcement requirement in that row passes. DENY is unconditional for that role on that capability. A missing prerequisite or unresolved deployment gate means DENY, even for developer_admin.

## 2. Universal Security Contract

The following apply to every row. G gates admitted operations, E gates two pre-admission rows, H gates exact own-link resolution, and P gates protected operational procedures. Identity exceptions are not application-role grants.

**G — admitted caller gate**

Validate Firebase identity and verified email; resolve only auth_links/{firebaseAuthUid}; require link.active = true, an existing users/{userId}, users.active = true, users.login_enabled = true, and a recognized users.access_role. Unknown/missing security values, broken relationships, and unknown/unlisted capability keys deny access. Validate the gate on backend requests and revalidate current authority at sensitive commit time.

**V — record and write validation**

Only the named target resource and field set are accessible. For creates, reject fields outside the stated creation set. For updates, check changed fields rather than accepting a whole-document overwrite. Preserve immutable IDs/references and creation metadata unless a row expressly permits otherwise. Validate required types and references against DATA_MODEL.md. All machine dates are Timestamp (or explicitly permitted null), never strings or a silent DateTime.now() fallback. Required unknown/malformed dates fail validation.

Actor IDs are application User IDs resolved from the caller. Audit/write times are server-controlled. A client cannot choose actor IDs or force arbitrary audit timestamps.

**S — sensitive workflow contract**

Sensitive security-state transitions are atomic within their Firestore mutation/audit boundary, idempotent, and audited. Check both existing target role and proposed role/state. Concurrent operations must preserve one active auth link per User. Composite approval may validate newly created User/link references against its atomic post-state, but must authorize the caller against current pre-state and enforce every participating capability. It cannot manufacture caller authority inside the batch. An operation ID reused with different input is rejected; an exact retry has no duplicate side effects and does not expose data to a caller who is no longer authorized. A backend must not rely on client Security Rules to authorize Admin SDK writes.

A leader cannot create, modify, link, disable, demote, or take over a developer_admin, including indirectly through request approval, User overwrite, auth-link replacement, donor linkage, or a generic endpoint. Generic account-security paths exclude existing developer_admin targets for every caller; protected operational procedure is mandatory. The explicit non-security own-profile capability is not an account-security management path.

**O — ordinary target boundary**

Ordinary targets are users whose current access_role is member, committee, or executive. Leaders may manage them only under explicit rows and may not perform role, active-state, login, or auth-link management on self, another leader, or developer_admin. Developer_admin-only leader-target rows explicitly cover disable/reactivate, login enable/disable, and auth-link create/replace; they do not permit managing a developer_admin target. Lower-role reassignment of a leader by developer_admin remains governed by the role.assign_* rows.

**P — protected administrative procedure**

Developer-admin provisioning/recovery is operational, using trusted administrative controls outside ordinary application management UI. Never expose developer_admin in normal role-assignment dropdowns. All five application-role cells for admin.provision/admin.recover are DENY: an application role/token alone cannot invoke an operational grant. Operational credentials/custody are not a sixth application access role.

Require verified target identity, strong administrative authentication, explicit operation/field scope and reason, preservation of recovery access, and atomic/idempotent audited writes. Account-security changes to an existing developer_admin use P; the explicit six-field own-profile edit is available to any admitted User, including a developer_admin editing self, and never permits security/identity changes.

The operational runbook must name custodians, credential controls, target verification, allowed actions, and recovery checks before execution. No application provisioning/recovery endpoint is authorized. Emergency recovery may use trusted operational controls without an admitted application session; it must not infer application privileges from missing fields.

**E — Firebase-authenticated pre-admission exception**

A verified Firebase token identifying a requester with NO auth_links/{request.auth.uid} document grants only registration.create_own and registration.read_own_status. Email verification is not an E prerequisite; it remains mandatory for approval/protected admission. Missing application access_role is expected in E and does not grant any business capability. E is an actor condition, not a new role. Existing inactive/broken links disqualify E. No users, user_directory, donors, committee data, donations, notices, or blood_requests read is permitted.

**H — exact own-link resolution**

H — minimal identity self-read: any Firebase-authenticated identity may get exactly auth_links/{request.auth.uid} to resolve admission, even before G can pass. No list/query, other-link get or client create/update/delete. The identity-based read is not an application role grant, and the link alone never grants admission. Protected operations still require verified email, active link, existing active User, login_enabled true and recognized users.access_role.

**Q — controlled User/directory synchronization**

Q preserves exact User/directory equality. Privileged User creation/state/security/photo changes and projection backfill/repair use trusted execution: reread current authoritative User, validate the originating capability, and commit the User, exact six-field directory projection and required audit evidence atomically. No stale asynchronous repair is allowed.

Free-V1 exception: an admitted caller may update an existing own User's name, phone, blood_group, profession, address and preferred_language only. Rules bind updated_at to request.time (serverTimestamp) and updated_by to the resolved own User ID; those metadata effects are not applicant-selected audit authority. photo_url remains operational/provider-controlled. Email, roles, active/login, links, creation metadata and all other security fields remain immutable in this client path.

For a directory-visible change, an atomic batch/transaction must include both users/{ownUserId} and user_directory/{ownUserId}. Rules use getAfter() to prove the directory post-state equals exactly name, phone, blood_group, profession, photo_url, active from the authoritative User post-state, with no extra fields. Both existing pre-state documents must be valid and synchronized; clients cannot create a missing projection or repair corruption. The directory rule independently binds the actor, exact own path, originating allowed User change and post-state metadata. No other-user, standalone, forged or stale directory writes pass. Non-directory-only edits may omit a directory write if exact post-state equality remains true.

Validate both sides, complete schema/changed-field allowlists, pre-state admission and rule-access-call limits. No client User/projection deletion, no generic directory writer and no directory authorization authority are introduced. Privileged and operational writers still apply trusted Q. If the Rules proof fails, the affected client write remains denied; there is no asynchronous or permissive fallback.

**Trusted execution**

TRUSTED EXECUTION means a reviewed operator-invoked local trusted tool in Free V1, or a hosted trusted backend in a separately approved future Blaze architecture. The local tool is not Flutter, is not distributed to application users and never embeds credentials in the APK. It runs only on an authorized operator machine using approved operational Google/Firebase credentials. It independently enforces capability, caller/target, state, field and provenance rules; implements required atomic/idempotent Firestore transactions and audit evidence; and fails closed. Operational credentials bypass client Security Rules and therefore require independent enforcement and protected custody. Ordinary application roles confer no operational IAM privilege. Sequential Console edits are not an atomic substitute.

## 3. Enforcement and Audit Legend

Every matrix row includes one of these enforcement paths:

| Path | Meaning |
|---|---|
| Firestore Rules | Direct application read/write is authorized by rules. Backend equivalents must independently enforce the same contract; this label does not grant an additional backend capability. |
| Trusted Execution | Internal trusted-execution-only operation; no application role can invoke it as an unrestricted writer. Client access is denied by rules. |
| Both | The trusted execution performs the mutation with independent authorization; Firestore rules reject the equivalent direct client mutation. For directory.sync, Both means trusted privileged Q plus the explicitly constrained Rules effect of user.own_profile_edit. No other Both row authorizes its privileged direct Flutter mutation. |

UI visibility is derived from this contract and never substitutes for backend enforcement. Capability keys sent by a client do not authorize themselves; each endpoint/write pattern must match a fixed supported operation.

Audit codes:

- **A0:** No separate audit_logs event required for this read or denied operation. Security failures may produce redacted operational telemetry.
- **AM:** Enforce the named entity metadata; the supplied policy does not require a separate privileged-action log for this normal write.
- **AP:** Required trusted privileged-action event, using the capability key as action, with authenticated actor, target, outcome, operation ID, server time, and minimal relevant change/reason.
- **AS:** AP plus atomic sensitive Firestore state/audit commit and S.
- **AT:** Internal creation of AP/AS evidence. Backend-owned append-only log; no recursive audit-of-audit requirement.

No role, including developer_admin, may directly create, alter, or delete audit_logs. Passwords, tokens, and unnecessary patient/contact data never enter them.

## 5. Shared Test Requirements

Every row's test cells incorporate these suites:

- **T+**: With valid fixtures and all prerequisites, test each ALLOW role separately; verify exact scope, returned data, field changes, and audit requirements. For Both backend mutations, test a valid authorized endpoint call and denial of the equivalent client write.
- **T-**: For every row, test each DENY role, unauthenticated caller, unverified email, absent/inactive link, inactive User, login disabled, missing/unknown access_role, and unknown capability. Test a member with position = president and historical leadership records: no extra permissions. Repeat with localized position labels.
- **W-**: For write rows, test extra/forbidden fields, spoofed actors, malformed Timestamp values, stale state, broken references, unexpected deletes, and whole-document overwrite attacks.
- **S+ / S-**: For sensitive rows, test exact retry without duplicate effects/audits, concurrent operations, altered-payload retry rejection, revocation before commit, and atomic failure rollback.
- **P-**: On every leader-capable account path, try an existing/proposed developer_admin target and indirect takeover; all must fail. Generic endpoints must reject protected-admin operations for every role.
- **R-**: Read tests include direct document get, queries, cross-record access, and attempts to recover restricted fields/history via response payloads, aggregation endpoints, or locally filtered results.

For E rows, the five role columns are DENY because no grant is made on the basis of an application role; the explicitly stated E requester grant is ALLOW independently. Test E rather than requiring G for these rows. H similarly grants exact identity self-read independently of application roles. All other all-DENY rows have no positive application grant. Their positive test verifies successful enforcement of denial or, only where stated, an internal authorized backend action. Test descriptions are specifications; no tests or features are implemented by this document.

- **E+ / E-**: Authenticated unlinked requester creates/reads exact own request; allow unverified email under E. Deny other UID, existing inactive/active/broken link, spoofed/missing token, list/update/delete, extra fields or nonconforming fixed state/actor/time/role/link fields, and every protected collection read. Read of own terminal decision remains allowed only while unlinked. Creation retries do not overwrite an existing decision.
- **Q+ / Q-**: Update each of the six own fields; verify exact six-field directory projection and forbidden-field exclusion. Reject standalone/forged/client repair directory writes and spoofed metadata; permit only valid atomic own-profile projection effects, rollback partial User/directory failure, and prevent stale retry/repair reactivation. Self-edit must not grant access to another private User.
- **C+ / C-**: Reject a second concurrent active assignment for the same User/term; allow same position for different Users and assignments in different terms. Historical inactive assignments do not consume the active slot.

## 14. Cross-Layer Conformance

Each row is read with its actor gate, field sets, state/scopes, and shared tests.

Decision order:

1. Unknown/unlisted capability: DENY.
2. auth_link.read_own: evaluate H only; all-DENY role cells do not cancel its identity-only get. registration.create_own / registration.read_own_status: evaluate E only. Their all-DENY application-role columns grant nothing by role and do not cancel the explicit Firebase-authenticated unlinked-requester grant. Do not require or synthesize an application role for E.
3. Operational admin.provision/admin.recover and internal audit/directory writers: no application-role grant. Require their trusted operational/originating-operation controls.
4. Every admitted application row: require G and ALLOW for the current users.access_role, plus every row constraint.

users.access_role remains the only current application role authority. Directory records, committee positions/history, display language, and client-selected capability keys never supply authority.

- Flutter: expose only applicable capabilities. Never offer developer_admin in normal role dropdowns or operational provisioning/recovery in ordinary management UI.
- Firestore Rules: enforce exact own User reads, active directory audience, listed business audiences, E's exact create/status contract and H's exact self-link get. Deny privileged direct writes and directory writes outside the atomic own-profile Q exception.
- Trusted execution: verify current identity/caller/target/state independently of Rules for all privileged workflows, auditing and operational Q. Own-profile and E create use their narrow Rules paths; approval/linking do not.
- Authorization tests: instantiate every row's actor/role decisions, scope, fields, and state transitions. Verify direct Firestore denials independently from trusted execution permissions.

user.profile_edit is an explicitly enumerated compatibility alias of user.own_profile_edit. user.directory_read is an explicitly enumerated compatibility alias of directory.view and targets user_directory only. Canonical keys are preferred; aliases must resolve to identical scoped decisions, not separate broad management behavior.

All User creation/profile/active/security writes that touch the authoritative User use Q. Any deployment/import/recovery writer must respect that invariant. No asynchronous stale projection is accepted as authority for repair.

Committee assignment creation is serialized for the User/term active slot; no duplicate active assignment survives concurrent requests. Different Users can hold the same position; different terms are independent. Exact retries do not create duplicate assignments.

Donation recording remains a trusted consistent event/aggregate mutation. Committee may record but may not read history, including its own recorded event. Return a minimal acknowledgement/event ID, not historical/recipient data. V1 donation lifecycle is controlled historical correction by developer_admin/leader; no hard delete or invented archive schema.

Blood-request terminal history is a separate read grant for developer_admin/leader/executive. Committee/member cannot read it even as creators; terminal read never allows edit, reopen, or delete. Mutation receipts remain minimal and do not implicitly widen audiences.

Normal donor creation/edit and blood-request creation may remain direct authorized Firestore writes. No unnecessary backend wrapper around all application operations is required.
